Anthropic, Claude로 신약 개발 가속한 초기 성과 공개

Anthropic 생명과학팀이 10월 27일 신약 개발사 6곳과의 협업 결과를 발표했다. Generate Biomedicines에서는 과학자 6명이 Claude Code로 CAR-T 설계를 제안했고, 표준보다 약 70% 짧은 설계가 실험에서 수용체를 약 10배 더 만들었다. Enveda에서는 1,061쪽 서류에서 사람이 찾은 문제 11개를 모두 잡고 7개를 더 찾았으며, 검토 시간이 25시간 넘게에서 3시간 미만으로 89% 줄었다. Anthropic은 아직 초기이고 대부분 전임상 단계라고 밝혔다.

그래서 무엇을 하나

Claude Code를 코드 밖 업무(대량 설계 탐색, 긴 문서 검토)에 쓰는 사례로 읽어 볼 만하다. 내 업무에서 사람이 검토하던 긴 문서 하나를 골라 Claude가 찾은 문제와 사람이 찾은 문제를 나란히 비교해 보자.

OpenAI와 Anthropic은 왜 몇 달 만에 LLM 값을 최대 80% 내렸나

의견 · 칼럼Max Woolf가 6월부터 9월까지 OpenAI와 Anthropic의 가격 인하를 표로 정리했다. Claude Opus 5.5는 입력 $4, 출력 $20, 캐시 읽기 $0.20(100만 토큰당)이고, Fable 5.1은 캐시 읽기를 $1에서 $0.25로 75% 내렸다. 글쓴이는 모델 전환 비용이 거의 없고 오픈 웨이트 모델이 압박하기 때문에 값이 다시 오르기 어렵다고 본다. 에이전트 코딩에서는 캐시 읽기가 토큰 비용의 96~99%라서, 캐시 가격 75% 인하가 실제 비용을 약 70~75% 줄인다고 설명한다.

그래서 무엇을 하나

에이전트 코딩 비용을 볼 때는 입출력 단가보다 캐시 읽기 단가를 먼저 비교하자. 지금 쓰는 모델의 캐시 읽기 가격을 한 번 확인해 두면 모델 선택 기준이 분명해진다.

OpenShell 설치 · 사용법: 에이전트를 샌드박스에 넣고 접근을 하나씩 승인하기

OpenShell은 NVIDIA가 공개한 자율 에이전트용 런타임이다. 에이전트마다 샌드박스를 만들고, 파일·네트워크·프로세스 규칙을 정책으로 강제한다. API 키는 OpenShell의 자격 증명 저장소에 두고 승인된 엔드포인트로 가는 요청에만 넣으므로 에이전트는 실제 키를 보지 못한다. 공식 첫 실습은 OpenCode와 OpenRouter 무료 모델을 쓰므로 비용 없이 따라 할 수 있다.

설치 · 설정

curl -LsSf https://raw.githubusercontent.com/NVIDIA/OpenShell/main/install.sh | sh
  1. Linux 또는 Apple Silicon macOS에 Docker나 Podman이 있는지 확인한다.
  2. 설치 스크립트를 실행한다. CLI와 로컬 게이트웨이가 함께 설치된다.
  3. openshell sandbox create --name demo 로 빈 Ubuntu 샌드박스가 뜨는지 확인한다.
  4. OpenRouter API 키를 OPENROUTER_API_KEY 환경 변수에 넣는다.
  5. (선택) npx skills add NVIDIA/OpenShell 로 코딩 에이전트에 OpenShell CLI·정책 작성 스킬을 넣는다.

실습

OpenCode 에이전트를 샌드박스에서 돌리고, 정책에 막힌 접근을 직접 승인해 본다.

  1. openshell profile import --url https://raw.githubusercontent.com/NVIDIA/OpenShell/main/providers/openrouter.yaml
  2. openshell provider create --name openrouter --type openrouter --from-existing
  3. openshell sandbox create --name my-agent --from ghcr.io/anomalyco/opencode:latest --provider openrouter -- opencode -m openrouter/nvidia/nemotron-3.5-lightning:free
  4. 샌드박스 안의 OpenCode에 인터넷에서 무언가를 받아 오는 작업을 시켜 정책에 막히게 한다.
  5. 다른 터미널에서 openshell rule get my-agent --status pending 으로 대기 중인 규칙 제안을 본다.
  6. 필요한 것만 openshell rule approve my-agent --chunk-id <chunk-id> 로 승인한다.
  7. 필요 없는 것은 openshell rule reject my-agent --chunk-id <chunk-id> --reason "Not needed for this task." 로 거절한다.
  8. 승인한 규칙은 실행 중인 샌드박스에 바로 반영되므로 에이전트에게 다시 시도하게 한다.

바로 쓰는 프롬프트

스킬 설치 뒤 개념 파악

OpenShell 스킬을 참고해서, 지금 내 머신의 OpenShell 샌드박스 목록과 각 샌드박스에 걸린 정책을 요약해 줘. 명령은 실행 전에 먼저 보여 줘.

대기 중인 규칙 검토

openshell rule get <샌드박스 이름> --status pending 결과를 보고, 각 제안이 어떤 호스트·경로를 여는지, <이번 작업 목적>에 꼭 필요한지 표로 정리해 줘. 승인은 내가 직접 할게.

프로젝트용 정책 초안

<프로젝트 경로>에서 에이전트가 해야 할 일은 <작업 설명>이야. OpenShell 스킬을 참고해 이 작업에 필요한 최소한의 파일·네트워크 접근만 허용하는 샌드박스 정책 초안을 써 줘. 적용은 하지 말고 파일로만 저장해 줘.

안 될 때

openshell rule approve-all 을 실행했는데 일부 제안이 승인되지 않고 남는다.
보안 표시가 붙은 제안은 기본으로 건너뛴다. 내용을 확인한 뒤 정말 필요하면 --include-security-flagged 를 붙인다.
제안 하나를 승인한 뒤 나머지 제안 목록이 달라졌다.
승인할 때마다 남은 제안을 다시 검사한다. 다음 승인 전에 openshell rule get <샌드박스> --status pending 으로 목록을 다시 본다.

주의. WSL 2 지원은 실험 단계다. 익명 텔레메트리가 기본으로 켜져 있으며, 게이트웨이에 OPENSHELL_TELEMETRY_ENABLED=false 를 주면 끈다. README에는 Claude Code를 샌드박스에서 돌리는 절차가 없으므로 공식 실습은 OpenCode로 한다.

에이전트가 막힌 곳에 닿을 때마다 규칙 제안을 받아 직접 승인하는 흐름을 손에 익힌다.

andrej-karpathy-skills 설치 · 사용법: Claude Code의 과잉 구현을 CLAUDE.md 하나로 줄이기

Andrej Karpathy가 지적한 LLM 코딩의 흔한 실수를 바탕으로 만든 CLAUDE.md 한 개다. 생각 먼저, 단순함 먼저, 외과적 수정, 목표 중심 실행의 네 원칙을 담았다. 이번 주 GitHub 트렌딩에서 주간 별 4,250개를 받았다. 플러그인으로 모든 프로젝트에 깔거나, 한 프로젝트의 CLAUDE.md에만 붙일 수 있다.

설치 · 설정

/plugin marketplace add forrestchang/andrej-karpathy-skills
  1. Claude Code를 연다.
  2. /plugin marketplace add forrestchang/andrej-karpathy-skills 로 마켓플레이스를 추가한다.
  3. /plugin install andrej-karpathy-skills@karpathy-skills 로 플러그인을 설치한다.
  4. 한 프로젝트에만 쓰려면 플러그인 대신 curl -o CLAUDE.md https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md 를 쓴다.
  5. 이미 CLAUDE.md가 있으면 echo "" >> CLAUDE.md 뒤에 curl https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md >> CLAUDE.md 로 끝에 붙인다.

실습

같은 버그 수정 요청을 설치 전후로 시켜 diff 크기와 확인 질문을 비교한다.

  1. 작은 버그 하나가 있는 브랜치를 고른다.
  2. 설치 전에 버그 수정을 요청하고 git diff --stat 결과를 적어 둔다.
  3. git stash 로 변경을 치운다.
  4. 플러그인을 설치하거나 CLAUDE.md에 내용을 붙인다.
  5. 새 세션에서 같은 요청을 다시 한다.
  6. 수정 전에 가정이나 해석을 먼저 말하는지 본다.
  7. git diff --stat 으로 바뀐 파일 수와 줄 수를 설치 전과 비교한다.

바로 쓰는 프롬프트

가정 먼저 꺼내게 하기

<기능 설명>을 추가하고 싶어. 코드를 쓰기 전에 네가 하는 가정과, 요청을 다르게 읽을 수 있는 방식을 먼저 나열해 줘.

재현 테스트부터 고치기

<버그 증상>이 있어. 먼저 이 버그를 재현하는 테스트를 쓰고 실패하는지 확인한 다음, 그 테스트를 통과시키는 최소한의 수정만 해 줘.

외과적 수정 점검

방금 변경한 git diff를 보고, <작업 목표>에 꼭 필요하지 않은 수정이 섞였는지 줄 단위로 짚어 줘. 관련 없는 죽은 코드는 지우지 말고 목록으로만 알려 줘.

주의. README는 이 지침이 속도보다 신중함을 우선한다고 밝힌다. 오타 수정 같은 사소한 작업에는 전 과정을 다 밟을 필요가 없다. 프로젝트 고유 규칙은 따로 CLAUDE.md에 함께 적어야 한다.
